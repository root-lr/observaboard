# V2 roadmap

V2 makes ObservaBoard manageable from the central: "one-click integration" becomes literal, with no SSH. The full PRD, V1 to V3, describes the goals. This page maps each workstream to the existing code.

## Suggested order

| # | Workstream (PRD) | Starting point in the code | Notes |
| --- | --- | --- | --- |
| 1 | **G1 · Central API and registry** | new `observa-api` service in `assets/central/docker-compose.yml.tmpl`, routed by Caddy (`/api/observa/*`) | The registry replaces `central.yaml` (channels) and `tokens.yaml`. Reuse `project.Config` as the project model. |
| 2 | **G2 · Remote agent configuration** | `internal/agent`: `config.alloy` rendering moves to the API; the agent uses Alloy's `remotecfg` block | Keep `observa apply` as an offline mode. Thresholds and routing then move from the textfile metric to series published by the API. |
| 3 | **G3 · Web interface** | dedicated subdomain or path behind Caddy | "Add a server" (single-use token) and "add a service" wizards (from discovered containers: `discovery.docker` exposed by the agent's API). |
| 4 | **G4 · Multi-tenancy** | `X-Scope-OrgID` in Caddy based on the token; `auth_enabled: true` in Loki; Grafana organizations | Tokens are already per agent: they just need to be attached to an organization. |
| 5 | **G9 · Multi-language level 2** | `internal/instrument` (variables, Dockerfile lines per runtime), `internal/detect` (pom.xml, composer.json, *.csproj, Gemfile) | Java: `-javaagent` via `JAVA_TOOL_OPTIONS`, without changing the command. |
| 6 | **G5 · New presets** | see [presets.md](presets.md#writing-a-preset) | NestJS, Express, Next.js, Nginx, MySQL, RabbitMQ, MongoDB. |
| 7 | **G10 · Web frontend (RUM)** | `faro.receiver` in `assets/agent/config.alloy.tmpl`, exposed by Caddy | Public key per project; Web Vitals dashboard. |
| 8 | **G11 · Non-container applications** | `observa attach --process`; journald in the agent | |
| 9 | **G6 · Incident Playground** | `examples/django-shop/store/chaos.py` already exists | Add memory leak and queue saturation; `observa playground` command. |
| 10 | **G7 · SLOs** | rules generated like the thresholds (`assets/central/prometheus/rules.yml.tmpl`) | Multi-window burn rate. |
| 11 | **G8 · Correlation** | `send_exemplars` in `tempo.yaml.tmpl`, `--enable-feature=exemplar-storage` in Prometheus | Link from the latency graph to traces. |

## Known V1 debt

- **Dashboards:** one folder per project, generated from the registry, will replace the variable filter.
- **Celery:** only the `celery` queue (database 0) is monitored. Make the list of queues configurable on the Redis service.
- **Intentional removals:** the "service down" and "silent agent" alerts stay active for 24 h after an intentional removal. The V2 registry will tell a removal from a failure.
- **Token rotation:** today it requires reinstalling the agent. Add `observa agent rotate-token`.
- **Log masking:** filter sensitive patterns (tokens, emails, cards) in the agent, with `loki.process` and `stage.replace`.
